# БУД Апка

Мобільний прототип сервісу, який допомагає мешканцям і власникам житла знайти майстра для побутового ремонту. Проєкт створюється для лабораторних робіт із людино-машинної взаємодії та демонструє клієнтський і майстерський сценарії у .NET MAUI.

## Ідея продукту

Людина часто стикається з несправністю раптово, не знає точної технічної назви проблеми й не має документів на обладнання. «БУД Апка» має допомогти описати ситуацію простими кроками, додати фото, побачити відповіді майстрів і самостійно вибрати фахівця. Після вибору користувачі можуть обговорити деталі й занести час та домовленості у картку візиту.

Основні принципи продукту:

- Клієнт сам обирає майстра за профілем, відповіддю, рейтингом та іншою доступною інформацією. Автоматичного призначення немає.
- Заявку можна створити без технічної термінології; опис і фото допомагають пояснити проблему.
- Точна адреса має бути доступна лише обраному майстру. До вибору майстри бачать тільки район.
- Ціна у прототипі є довідковою пропозицією майстра. Оплата, ескроу та юридично обов’язкове підтвердження домовленостей не реалізуються.
- Паспорт техніки — добровільне доповнення. Він не має блокувати створення заявки або автоматично передавати необрані користувачем дані.

## Сценарії прототипу

**Клієнт:** обирає категорію та симптоми → за бажанням додає опис, фото й обладнання → вводить район та адресу → переглядає заявку → проходить демонстраційний вхід → переглядає відповіді й профілі → обирає майстра → спілкується в чаті → вручну записує дату/час → позначає виконання та залишає оцінку.

**Майстер:** активує демонстраційний профіль → переглядає локальний список тестових заявок → читає дозволені деталі → надсилає текстову відповідь і довідкову ціну.

Реалізовані екрани включають заявку та адресу, перегляд і демонстраційний вхід, пропозиції й профіль майстра, чат, деталі візиту, замовлення, профіль, режим майстра та паспорт обладнання. Перелік екранів і переходів реалізації можна знайти в `MainPage.ScreenRouter.cs` та `MainPage.*Screens.cs`.

## Межі та статус

Це навчальний інтерактивний прототип, а не готовий до запуску сервіс. Дані заявок, профілів, пропозицій, повідомлень і обладнання демонстраційні. Вибір теми зберігається локально.

### Локальне збереження

Чернетка, замовлення з пропозиціями, чатом, візитом і оцінкою, сповіщення, профіль,
профіль майстра, картки послуг і паспорт техніки зберігаються у версійованому файлі
`budapka-state.json` у приватному каталозі застосунку (`FileSystem.AppDataDirectory`).
Запис атомарний: спершу тимчасовий файл, потім заміна з резервною копією `.bak`.
Якщо основний файл пошкоджено, стан відновлюється з резервної копії. Файл іншої
версії схеми ігнорується. Вибрані фото копіюються в підкаталог `photos`, а невикористані
копії видаляються під час запуску. Відкритий екран, фільтри та код демо-входу не зберігаються.

У проєкті немає серверної частини, бази даних, реальної SMS-автентифікації, синхронізації чату, push-сповіщень, платежів, перевірки документів майстра, мапи чи OCR. Дані й приклади в інтерфейсі не є результатами дослідження користувачів. Не додавайте до звіту вигадані інтерв’ю, цитати або перевіреність майстрів.

Ручне заповнення паспорта обладнання — базовий сценарій. OCR є можливою майбутньою демонстраційною функцією лише після стабілізації основних шляхів; у разі невдалого розпізнавання користувач має продовжити вручну.

### Підтвердження виконання

Майстер може позначити роботу виконаною. Клієнт отримує сповіщення й підтверджує
завершення, після чого замовлення потрапляє в історію. Якщо клієнт не підтверджує
виконання, замовлення залишається активним із позначкою майстра. У прототипі
немає строку для підтвердження чи механізму вирішення спорів.

Після підтвердження клієнт може залишити одну оцінку з необов’язковим текстом одразу
або пізніше з картки завершеного замовлення. Відгук прив’язаний до замовлення та ID
майстра, повторно не зберігається й показується в профілі майстра разом із середньою
оцінкою. Демонстраційні оцінки й тестові відгуки позначені в інтерфейсі.

### Довідник адреси

Регіони та населені пункти вибираються з локальної копії КАТОТТГ від 07.07.2026.
Файл `Resources/Raw/UkrainianSettlements.txt` містить код регіону, код запису, назву
та громаду. Джерело — [КАТОТТГ Мінрозвитку](https://mininfra.gov.ua/diialnist/rozvytok-mistsevoho-samovriaduvannia/kodyfikator-administratyvno-terytorialnykh-odynyts-ta-terytorii-terytorialnykh-hromad).
Файл `UkrainianCityDistricts.txt` додає записи категорії B тієї самої редакції
для районів у містах. У зоні майстра можна зберегти регіон, населений пункт або район.
Стрічка за замовчуванням показує регіон, а фільтри звужують список за місцем і послугами.
Для вулиць доступні ручне введення й підказки системної служби карт на мобільних платформах.
Номер будинку необов’язковий. Квартиру можна повідомити майстру після узгодження часу.

## Технології та запуск

- .NET MAUI, один спільний проєкт.
- Цілі проєкту задаються у `BudApka.csproj`: Android, iOS, Mac Catalyst і Windows відповідно до ОС та встановлених workload-ів.
- Для роботи у Visual Studio потрібні відповідний .NET SDK і .NET MAUI workload.
- На Windows основна ціль для перевірки мобільної поведінки — Android. Можна запустити на фізичному Android-пристрої з увімкненим режимом розробника та USB debugging; емулятор для цього не обов’язковий.

Відкрийте `BudApka.slnx` у Visual Studio, виберіть Android-пристрій або Windows як ціль запуску та запустіть конфігурацію Debug. Для командного рядка Android-збірка виглядає так:

```powershell
dotnet build BudApka.csproj -f net11.0-android -c Debug
```

У Windows MSBuild за замовчуванням зберігає проміжні файли та APK під
`%LOCALAPPDATA%\BudApka\build`. Кожна робоча копія має власну підпапку, щоб
сервіси синхронізації робочого столу не блокували файли збірки.

Конкретні доступні target frameworks залежать від встановленої версії SDK та платформи розробки; за потреби звіряйте їх із `BudApka.csproj`.

## Структура коду

```text
App.xaml(.cs)                Глобальні ресурси й створення застосунку
AppShell.xaml(.cs)           MAUI Shell та корінь навігації
MauiProgram.cs               Конфігурація MAUI, шрифтів і залежностей
MainPage.xaml                Каркас головної сторінки
MainPage.xaml.cs             Спільний каркас, тема, навігація та UI-хелпери
MainPage.ScreenRouter.cs     Вибір екрана за поточним сценарієм
MainPage.*Screens.cs         Екрани заявок, замовлень, профілю, майстра й чату
MainPage.SharedViews.cs      Повторно використовувані елементи інтерфейсу
MainPage.Persistence.cs      Відновлення й збереження стану, події життєвого циклу вікна
LocalStateStore.cs           JSON-файл стану, атомарний запис і копії фото
ViewModels/                  Стан і логіка представлення
Resources/                   Стилі, кольори, зображення, шрифти й ліцензії
Platforms/                   Налаштування платформ
```

**Поточний стан архітектури:** це ранній прототип. Значна частина екранів зараз створюється C# кодом у файлах `MainPage.*Screens.cs`, а `PrototypeViewModel` містить спільний стан багатьох сценаріїв. Така організація не є кінцевою цільовою архітектурою.

**Напрям подальшого розвитку:** поступово перейти до MVVM без зайвих шарів. XAML описує екран, ViewModel зберігає стан сценарію та команди, а code-behind лишається для поведінки, безпосередньо пов’язаної з візуальним елементом. Для повідомлення про зміну властивостей і команд планується `CommunityToolkit.Mvvm`; додавати його слід у межах конкретного кроку рефакторингу. Зовнішні ефекти (файли, фото, Preferences, майбутній API) виносяться в сервіс тоді, коли вони реально з’являються. Не створюйте окремі проєкти, універсальні репозиторії, медіатори чи складні шари лише заради шаблону.

Порядок навігації та станів замовлення має залишатися простим і зрозумілим. Перед зміною сценарію перевіряйте узгодженість клієнтського та майстерського шляхів і вимоги приватності адреси.

## Стиль коду

Для C# діють правила з [`CODE_STYLE.md`](CODE_STYLE.md) та машинні налаштування з [`.editorconfig`](.editorconfig). `AGENTS.md` містить короткі вказівки для AI-асистентів. Форматування старого коду робіть окремим, переглядним кроком, не поєднуйте великий форматувальний diff із функціональними змінами.
