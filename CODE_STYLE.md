# Правила C# та архітектури

Це командна домовленість для «БУД Апки». Мета — зробити код читабельним і передбачуваним, не створюючи enterprise-архітектуру для навчального прототипу. Форматування у Visual Studio налаштоване в [`.editorconfig`](.editorconfig).

## Форматування

- 4 пробіли для відступів, не таби.
- Відкривальна фігурна дужка — на новому рядку. Фігурні дужки використовуються завжди, навіть для коротких `if`, `for`, `foreach`, `while` та інших блоків.
- Один вираз/оператор на рядок. Не зліплюйте оголошення, умову й дію в один рядок.
- Орієнтуйтеся на рядки до 100 символів. Якщо вираз або список аргументів довший, переносьте його на кілька рядків; рядки, що змушують горизонтально прокручувати редактор, залишати не можна.
- Довгі текстові повідомлення розбивайте на сусідні рядкові частини або збирайте з логічних фрагментів, не додаючи випадкових пробілів чи змін до показаного тексту.
- `using` розміщуйте на початку файла, поза namespace; `System` директиви сортуйте перед іншими.
- Використовуйте пробіли навколо операторів і після ком.
- Розділяйте порожнім рядком різні смислові блоки; не додавайте порожні рядки після кожного оператора.

Приклад:

```csharp
if (isReady)
{
    await SubmitAsync(request);
}
else
{
    ShowValidationMessage();
}
```

## Найменування

| Елемент | Стиль | Приклад |
| --- | --- | --- |
| Клас, struct, enum, метод | `PascalCase` | `RequestViewModel`, `SubmitAsync()` |
| Інтерфейс | `I` + `PascalCase` | `IRequestService` |
| Публічна/внутрішня властивість | `PascalCase` | `SelectedMaster` |
| Подія | Назва факту в `PascalCase`, без `On` | `Saved`, `ItemSelected` |
| Метод, що викликає подію | `On` + назва події | `OnSaved()` |
| Локальна змінна, параметр, local function | `camelCase` | `selectedMaster` |
| Приватне поле | `_camelCase` | `_currentScreen` |
| Асинхронний метод | Суфікс `Async` | `LoadOffersAsync()` |
| Член enum | `PascalCase` | `OrderStatus.Submitted` |

Імена мають передавати зміст. Не скорочуйте загальновживані поняття без потреби (`request`, а не `req`; `selectedMaster`, а не `sm`).

## Поля, властивості та Unity

- Поля — приватна внутрішня реалізація. Для доступу з іншого об’єкта використовуйте властивість або метод; не створюйте публічні змінювані поля.
- Для стану використовуйте найвужчу потрібну видимість. За можливості обмежуйте зміну значень (`private set`, `init`, `readonly` або незмінювані моделі — за ситуацією).
- У Unity дані для Inspector зберігайте в приватних полях `[SerializeField]`, також називаючи їх `_camelCase`. Публічну властивість додавайте лише якщо нею користується інший код:

```csharp
[SerializeField] private float _moveSpeed = 5f;

public float MoveSpeed => _moveSpeed;
```

- `[SerializeField]` є Unity-специфічним правилом і не переноситься в .NET MAUI код.

## Короткий синтаксис і типи

- Пишіть `string`, `int`, `bool`, а не `String`, `Int32`, `Boolean` у звичайних оголошеннях.
- Використовуйте `var`, коли тип очевидний з правої частини (`var offers = new List<MasterOffer>()`). Якщо тип неочевидний — назвіть його явно.
- Expression-bodied запис `=>` дозволений для простого виразу або очевидної властивості:

```csharp
public bool HasOffers => Offers.Count > 0;
```

- Якщо є кілька кроків, розгалуження або побічні дії, використовуйте звичайний блок із фігурними дужками.
- Обирайте зрозумілі ранні виходи й прості умови замість глибокої вкладеності та складних тернарних виразів.

## Події, callbacks і MVVM

- .NET-події, які є контрактом між об’єктами, оголошуйте як `EventHandler` або `EventHandler<TEventArgs>`. Назва події описує факт (`Saved`), а метод, що її піднімає, — `OnSaved`.
- `Action` або `Func` підходять для простого callback, який передається як параметр або має одного конкретного власника.
- У Unity зберігайте імена lifecycle callbacks рушія (`OnEnable`, `OnDisable`). Для власних подій фактів лишається правило `PascalCase` без `On`.
- У MVVM MAUI стан екрана — bindable properties, дії користувача — commands. Звичайний binding/command не потребує R3.
- R3 можна застосувати, якщо дійсно є потік значень чи подій, який потрібно комбінувати, обмежувати за частотою або керувати його життєвим циклом. Не додавайте R3 «про всяк випадок».

## Архітектурна домовленість для цього прототипу

- Зберігаємо один .NET MAUI проєкт. Не додаємо окремі проєкти Domain/Data чи шари лише заради шаблону.
- Ціль — MVVM без фанатизму: XAML для візуальної структури, ViewModel для стану сценарію й команд, code-behind — лише для UI-поведінки, яку природно важко виразити binding-ами.
- Коли почнеться рефакторинг, для властивостей і команд використовуємо `CommunityToolkit.Mvvm` замість ручного `INotifyPropertyChanged` там, де це спрощує код. Не переписуйте весь проєкт механічно лише заради використання атрибутів Toolkit.
- Групуйте ViewModel за екраном або зв’язним сценарієм. Не робіть один гігантський ViewModel для всього продукту й не створюйте клас для кожного дрібного тексту.
- Простий демонстраційний стан може жити у ViewModel. Сервіс додавайте, коли з’являється конкретний зовнішній ефект або спільна операція (наприклад, Preferences, фото, локальне сховище чи API).
- Використовуйте вбудований MAUI dependency injection для реальних залежностей. Не додавайте Prism, MediatR, generic repositories чи складну навігаційну інфраструктуру без конкретної потреби.
- Не плутайте демонстраційні дані з реальною авторизацією, чат-сервером, платежами чи дослідницькими результатами.

## Застосування до старого коду

`.editorconfig` підказує Visual Studio форматування та частину naming rules для нового/відформатованого C# коду. Нові правила не переписують старі файли автоматично. Під час рефакторингу форматування робіть окремим невеликим кроком і перевіряйте diff; не змішуйте повне перевпорядкування файлів із логічною зміною поведінки.
